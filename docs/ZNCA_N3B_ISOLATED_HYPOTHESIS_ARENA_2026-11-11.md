# ZNCA N3-B：隔离式竞争假设区

日期：2026-11-11  
状态：确定性参考原型；不是并行线程运行时，不是已训练模型。  
上游：ZNCA N3 架构提案；下游：N3-C 证据门控事务提交与持久化。

## 1. 目标

N3-A 负责确定哪些关系状态需要重新计算。N3-B 负责让多个候选解释从同一个认知状态版本分叉，并在隔离环境中保存各自的状态增量。候选不能直接修改共享状态。

## 2. 数据契约

每个 Hypothesis 包含：

- hypothesis_id：候选唯一标识；
- base_version：分叉时的认知状态版本；
- read_set：推演读取的状态键；
- write_set：候选准备修改的状态键；
- state_delta：只包含 write_set 的候选增量；
- evidence_refs：支持该候选的证据引用；
- status：PROPOSED / SUPPORTED / CONTESTED / REJECTED / COMMITTED / STALE。

所有候选都以同一个 Arena base snapshot 为起点。候选之间不共享可变状态。

## 3. 裁决和提交

1. propose 只登记不可变候选，不改变共享状态。
2. assess 要求候选拥有至少一个已登记证据引用；缺证据或未知证据进入 CONTESTED。
3. reject 将未提交候选终结为 REJECTED。
4. commit 只接受 SUPPORTED 候选。
5. 提交前检查已提交候选的读写集合。若先前写集合触及当前候选的读/写键，或先前读集合触及当前候选的写键，则当前候选进入 STALE。
6. 无冲突时，先在副本上应用 delta，再一次性发布新快照并递增版本。
7. 重复提交同一候选返回原提交结果，保证进程内幂等。

## 4. 关键性质

- 隔离：提出和评估候选不会改变共享状态。
- 确定性：候选枚举、快照键和冲突键排序稳定。
- 原子性：delta 完整应用后才发布新快照。
- 证据门控：未知证据不能升级为 SUPPORTED。
- 冲突安全：读写冲突不会静默覆盖。
- 有界性：本原型不执行搜索；候选数量由调用方预算控制。

## 5. 复杂度

对一个候选，证据门控为 O(E_h)，冲突检查为 O(C × (R_h + W_h))，状态快照复制和发布为 O(S)，其中 E_h 是候选证据数、C 是已提交候选数、R_h/W_h 是读写集合规模、S 是状态键数。该原型为清晰正确性参考，不是百万级状态存储或移动端性能实现。

## 6. 测试

运行：

```bash
python -m unittest tests.test_znca_n3b_hypothesis_arena -v
python -m unittest discover -s tests -v
```

覆盖隔离、证据门控、同基版本、读写冲突、写写冲突、非冲突兄弟提交、原子提交、幂等提交、拒绝终态、非法增量和未知读取键。

## 7. 明确限制与下一步

- 当前只在单进程内存中维护状态，没有多线程并行、锁、崩溃恢复或跨进程事务。
- 证据引用由调用方登记；尚未验证证据来源真实性、独立性或概率校准。
- 当前只做键级冲突检测；后续需支持关系对象版本、依赖闭包和语义冲突检测。
- 进程内幂等不等于持久化 exactly-once。
- 下一阶段 N3-C 应把提交写入 append-only event log，以 expected_version / compare-and-swap、事务 ID、证据策略版本和恢复测试实现持久化提交语义。
