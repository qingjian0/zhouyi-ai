# Shared Evidence Protocol v0.3: Compatibility Contract for CSL

Date: 2026-11-11  
Status: proposal / implementation gate  
Base integration tree: `f982d12c555b2f2254248faa4371a7f3d1ab113c`  
Pinned E09 adapter head: `e12a4e37508502dcaac07ffd01dd82e93ee4d3ca`  
Pinned E12-A6 × E02-D runner head: `9b6359180e1247428cee17395dfb3431e539544d`  
Current protocol implementation: v0.2, blob `062279e63b64cd6a3a8ad1ef38fc89c1b45251ce`

> This document is a contract proposal. It does not claim that protocol v0.3, CSL persistence, atomic multi-event batches, or crash-resumable learning has been implemented.

## 1. Why v0.3 is needed

The composed E12 + E09 smoke tree passes its current test suite (workflow run 42941694334, head `f982d12c555b2f2254248faa4371a7f3d1ab113c`). This establishes that the pinned source trees coexist and the included tests pass. It does not establish semantic integration.

Code inspection identifies a specific contract mismatch:

- E12-A6 support evidence is learner-visible TRAIN evidence supplied before the learner predicts. It is not necessarily the result of a prediction/reveal pair.
- Shared protocol v0.2 accepts only `evidence_reveal` event IDs in `structure_version.support_evidence_ids` and `revision.trigger_evidence_ids`.
- Requiring a prediction commit/reveal for every support item would fabricate a causal history and would incorrectly imply that pre-existing support was generated by post-prediction evaluation.
- The E12 lifecycle ledger has append-only actions, but those actions are not persisted in the v0.2 shared event store.
- The E09 adapter is fresh-episode-only and fail-closed after partial failures; it is not restart/replay capable.

The minimum extension is not a second ledger or a new lifecycle enum. It is a versioned event contract that can represent both pre-existing evidence ingestion and post-commit evaluator reveals, plus explicit lifecycle actions.

## 2. Design constraints

1. Preserve v0.1/v0.2 event bytes, digests, and replay meaning.
2. Never synthesize prediction commits or evaluator reveals for TRAIN support.
3. Keep evidence role, source provenance, learner track, and visibility explicit.
4. Keep evaluator-only truth outside learner-facing payloads and candidate-generation inputs.
5. Preserve E12-A6 as the domain transition validator; protocol events persist its accepted actions.
6. A changed candidate definition creates a new immutable structure version.
7. Reject unknown event types and unsupported lifecycle actions; no permissive fallback.
8. Make event append idempotent and sequence allocation transactional.
9. Distinguish a single-event atomic append from an atomic multi-event batch.
10. Do not claim process isolation, authentication, distributed consensus, or crash-resume until independently implemented and tested.

## 3. v0.3 event envelope

Every v0.3 event retains the v0.2 envelope fields:

```text
episode_id
sequence_no
event_id
event_type
protocol_version
payload_json
payload_digest
actor_role
causation_refs
payload_schema
integrity_metadata
created_at
```

New events use `protocol_version = "0.3"` and a concrete schema identifier such as `evidence_ingest@1`. Existing event types remain valid with their v0.2 semantic rules. New fields are not retroactively required on old rows.

The digest continues to cover event type, payload schema, payload, actor role, causation references, and integrity metadata. The protocol version is stored in the row and must also be included in the fingerprint in v0.3 so that semantically different schema versions cannot collide under the same idempotency key.

## 4. New event: evidence_ingest

Purpose: persist evidence that is already visible to the learner at the time of ingestion, including support examples and pre-episode training material. It is not an evaluator reveal.

Required payload:

```json
{
  "evidence_id": "opaque-evidence-id",
  "learner_track": "e12",
  "evidence_role": "TRAIN",
  "visibility": "LEARNER_VISIBLE",
  "source_ref": "opaque-source-reference",
  "observation_ref": "optional-observation-id",
  "content_digest": "sha256-of-canonical-evidence-content",
  "content": {
    "input": {},
    "target": null
  }
}
```

Rules:

- `evidence_id` is unique within an episode and learner track.
- `learner_track` is non-empty and explicit.
- Initial allowed `evidence_role` is only `TRAIN`. Do not permit GATE, LOCKED_TEST, or POST_DEPLOY in this event.
- `visibility` must equal `LEARNER_VISIBLE`; evaluator-private content is not admissible.
- The event is append-only. Corrections are new evidence with a new ID and explicit supersession metadata; old evidence is not overwritten.
- `content_digest` must match canonical content. The store can verify the digest but cannot prove that the caller truthfully classified visibility or role.
- The protocol must not infer causal order from source timestamps. The event sequence is the authoritative order of ingestion.
- Support evidence is eligible as structure support only when the structure and evidence share the same learner track, and the evidence role is permitted by the structure's declared support policy.

The `content` field is shown as a reference shape. Implementations may store a content reference rather than raw content, but must define retention and availability semantics. The learner must receive the actual content through a controlled interface before claiming it learned from that evidence.

## 5. Existing event: evidence_reveal

Keep `evidence_reveal` for feedback released after a committed prediction. It must retain the v0.2 invariant:

`observation -> prediction_commit -> evidence_reveal`

A reveal must cite exactly one prior prediction from the same learner track. It must not be used to disguise support data that was visible before prediction. The event's actor role remains evaluator, but actor_role is metadata rather than authentication.

## 6. Structure support and revision references

v0.3 extends support references to a tagged reference object rather than treating every reference as an evidence_reveal event ID.

Recommended shape:

```json
{
  "support_refs": [
    {
      "evidence_event_id": "episode:train:evidence-1",
      "evidence_kind": "INGESTED_TRAIN"
    },
    {
      "evidence_event_id": "episode:reveal:reveal-prediction-1",
      "evidence_kind": "POST_COMMIT_REVEAL"
    }
  ]
}
```

Compatibility rules:

- v0.2 `support_evidence_ids` remains readable and means prior `evidence_reveal` event IDs only.
- v0.3 `support_refs` may point to `evidence_ingest` or `evidence_reveal`, subject to role and track checks.
- Do not silently reinterpret a v0.2 identifier as an ingested TRAIN event.
- During migration, preserve original payload JSON and digest. Expose a normalized read model with explicit `evidence_kind`; do not rewrite old event bytes.
- Revision triggers may include post-commit reveals and explicitly allowed learner-visible ingested evidence, but every trigger must record its evidence kind and track.
- Gate and Locked-Test evidence must never be silently added to learner-visible support references before their release protocol allows it.

## 7. New event: lifecycle_action

Purpose: persist an action already validated by the E12-A6 domain ledger. This event records a transition; it does not independently authorize an illegal transition.

Required payload:

```json
{
  "action_id": "opaque-action-id",
  "learner_track": "e12",
  "candidate_id": "candidate-17",
  "candidate_version": 2,
  "action_type": "CHALLENGE",
  "from_state": "GATE_VALIDATED",
  "to_state": "CHALLENGED",
  "evidence_refs": [
    {
      "evidence_event_id": "episode:reveal:reveal-prediction-1",
      "evidence_kind": "POST_COMMIT_REVEAL"
    }
  ],
  "reason_code": "LOCKED_TEST_COUNTEREXAMPLE",
  "domain_contract": "e12a6-lifecycle@<pinned-version>",
  "domain_action_digest": "digest-of-the-validated-domain-action"
}
```

Rules:

- v0.3 must enumerate supported E12-A6 action types from the exact pinned contract; do not accept arbitrary strings.
- The store validates event shape, referenced versions/evidence, track consistency, and sequence order. The E12-A6 ledger validates legal state transitions.
- The adapter must validate the transition before appending the event. If validation fails, no lifecycle event is appended.
- A lifecycle event must not mutate an existing structure definition.
- Unsupported semantic phases (including CSL-only UNDER_TEST/PROVISIONAL/ACTIVE/SUSPENDED unless explicitly mapped) must remain unsupported or derived views. Do not create a parallel state machine.
- SPLIT and MERGE require explicit parent/child lineage and action semantics. They are not assumed to exist in the pinned E12-A6 action contract.
- Retirement/challenge events remain historical and replayable; no deletion or destructive update is allowed.

## 8. Atomic append batch

A multi-step transition often needs a structure version and a revision record to become visible together. Separate successful single-event appends can leave a semantically incomplete prefix if the process fails between them.

Add an API conceptually equivalent to:

```python
store.append_batch(
    episode_id=episode_id,
    batch_id=batch_id,
    events=[event_1, event_2, ...],
    expected_sequence=current_sequence,
)
```

Contract:

- All events in one batch are validated in sequence against the transaction's prior rows plus earlier events in the same batch.
- All events commit in one SQLite transaction, or none commit.
- Batch idempotency is bound to the ordered list of complete event fingerprints.
- Repeating the same batch ID and identical payload returns the original receipts; reusing it with different content raises an idempotency conflict.
- A failure in event N rolls back events 1..N-1 and sequence allocation; no sequence gaps are created.
- Single-event `append_event` remains supported and can be implemented as a one-event batch.
- Do not claim that this makes learner memory crash-resumable. It only makes the event batch atomic. Reconstructing E09/E12 runtime state from replay is a separate requirement.

## 9. Replay and compatibility behavior

Replay must be deterministic over ordered event rows and the exact schema versions.

- v0.1 rows: preserve original bytes/digests; expose the legacy learner-track compatibility view as already specified by v0.2.
- v0.2 rows: preserve current five-event semantics.
- v0.3 rows: validate the new event types and tagged evidence references.
- Unknown future protocol versions: fail closed for state reconstruction; raw event export remains possible.
- Unknown event types: fail closed for semantic replay; do not skip them and continue with a potentially incorrect state.
- Replaying the same event stream with the same pinned learner and adapter versions must produce the same candidate-state projection and structure-version graph.
- Event timestamps are diagnostic only. Sequence number and explicit causation references determine causal order.

## 10. Required conformance tests

### Evidence ingestion

1. TRAIN evidence can be ingested without a prediction commit.
2. GATE and LOCKED_TEST roles are rejected by `evidence_ingest`.
3. Empty learner track, duplicate evidence ID, malformed digest, and learner-private visibility are rejected.
4. Structure support can reference a prior ingested TRAIN event in v0.3.
5. A structure cannot reference another learner track's evidence.
6. v0.2 support references continue to require a prior reveal event.

### Lifecycle actions

7. A legal E12-A6 action can be persisted after domain validation.
8. An illegal transition is rejected before persistence.
9. A lifecycle action referencing future or unknown evidence/version is rejected.
10. A mismatched candidate version or learner track is rejected.
11. A changed definition requires a new structure version and parent reference.
12. Unsupported CSL-only states/actions are rejected, not silently normalized.

### Atomicity and idempotency

13. A batch with a failure in its final event leaves no earlier batch event committed.
14. Repeating an identical batch is idempotent and returns the same event receipts.
15. Reusing a batch ID with changed event content fails.
16. Concurrent writers using stale expected sequence cannot create duplicate sequence numbers.
17. A failed batch does not leave sequence gaps or idempotency rows.

### Replay and migration

18. v0.1 and v0.2 fixtures replay with unchanged event digests.
19. v0.3 ingested TRAIN and post-commit reveal remain distinguishable after replay.
20. Unknown event type/version fails closed.
21. Replaying the same ordered stream twice yields byte-equivalent normalized state projections.
22. Crash-injection tests at transaction boundaries confirm all-or-none batch persistence.

### Leakage and trust boundaries

23. Mutating evaluator-only truth cannot change learner-visible evidence before reveal.
24. Candidate IDs, event IDs, timestamps, source refs, and metadata are randomized independently of hidden mechanism and seed.
25. No evaluator-private label or generator field appears in learner-facing candidate/proposer inputs.
26. Changing hidden truth while holding learner-visible observations and metadata fixed leaves all pre-reveal learner decisions unchanged.

Passing these tests establishes protocol/conformance properties only. It does not establish learning improvement or security against a malicious process with direct database access.

## 11. Migration and implementation sequence

1. Pin the exact source commits listed at the top and preserve the integration-smoke commit as the compatibility baseline.
2. Add protocol v0.3 schema definitions and fixture tests without changing v0.2 behavior.
3. Implement `evidence_ingest` and tagged `support_refs`; verify TRAIN support can be persisted without fabricating a reveal.
4. Implement `lifecycle_action` as a persistence adapter over the E12-A6 validator; reject unsupported states/actions.
5. Implement atomic `append_batch` and test rollback/idempotency/concurrency.
6. Add replay projection for mixed v0.1/v0.2/v0.3 event streams.
7. Add E12 adapter and E09 adapter conformance tests separately; do not assume E09's current adapter can resume.
8. Only after these pass, build the smallest E12 + E09 joint episode. Keep Gate and Locked-Test behind a separate evaluator interface.
9. Run leakage mutation tests and a preregistered small benchmark before adding E03 arbitration or classical priors.

## 12. Explicit non-goals

This proposal does not implement:

- a distributed event broker or multi-host consensus;
- cryptographic actor authentication or tamper-proof provenance;
- process-level evaluator/learner isolation;
- restart/resume of a live E09 or E12 learner;
- automatic cross-track dependency invalidation;
- a general CSL lifecycle enum;
- E03-B coordination;
- neural concept learning or a Transformer replacement.

Those are separate research and engineering questions.

## 13. Decision

Adopt the v0.3 proposal as the next implementation target only after review of the exact E12-A6 and E09 contracts. The immediate measurable win is semantic honesty: TRAIN support is represented as TRAIN ingestion, post-prediction feedback remains a reveal, and lifecycle transitions become auditable without inventing causal events or duplicating state machines.
