# 易象类象：有出处的八卦语义档案 v0.1

## 为什么增加这一层

当前编码模块已经能稳定表示阴阳爻、八卦、六十四卦和爻变；类象 MVP 能校验显式映射的关系保持。但两者之间仍缺少一个关键层：**可追溯的传统语义资料层**。

如果程序直接把“乾=某属性”“坎=某过程”等解释写死，就会把特定注本、象数传统或后世解释误当成唯一事实。这样不仅无法处理异说，也会让模型把人为设定当成训练标签。

本版本增加 source-grounded profile：八卦的三爻编码是稳定的结构约定；每一条语义主张则必须绑定来源、版本、定位和适用范围。程序只验证数据完整性，不替研究者裁定经典解释。

## 数据结构

- SourceRef：书名、版本/整理本、精确定位。
- TrigramProfile：卦名、三爻自下而上编码、传统/解释体系标识、版本。
- SourcedClaim：主语、谓词、对象、来源 ID、主张级精确定位、主张类型、审核状态、适用范围及稳定 claim ID。
- ProfileConflict：同一主语/谓词/范围出现不同对象时显式报告；不自动覆盖、投票或合并。

## 已实现约束

1. 八卦编码沿用项目既有约定：阳=1、阴=0，爻序自下而上。
2. 名称与三位编码必须一致；拒绝 bool、浮点数和长度错误。
3. 每条语义主张必须引用已登记来源，并提供主张级精确定位；仅引用整本书或整章不足以审计具体主张。
4. 来源类型区分经典原文、历史注疏、现代研究、现实观察、研究假设、合成样本和模型生成内容。
5. 主张类型区分传统文本主张、注疏主张、现代解释、项目操作定义、研究假设、观察主张和合成夹具。
6. 主张审核状态只能是未审、已审、存疑或驳回；模型生成内容不能自动升级为已审。
7. 来源 ID、档案 ID 和主张 ID 必须在档案集中唯一。
8. 冲突按“主语 + 谓词 + 适用范围”检测；不同范围的解释不会被误报为冲突。
9. 多个解释传统并存，不隐式判定哪个传统正确。

## 类象研究的下一步数据闭环

八卦档案不是类象本身。完整链路应为：

1. **取象**：从文本、图像、事件或结构化数据提取候选对象/属性/关系，并保留原始证据定位。
2. **定象**：将候选挂接到一个明确版本的概念档案；未能定位来源的内容保持未审定。
3. **比类**：提出源域—目标域映射，分别比较形态、属性、功能、关系、过程、时空、势象。
4. **验类**：检查关系保持、条件匹配、反例和任务结果；结构相似不能替代语义证据。
5. **变类**：新证据出现时允许修订、拆分或撤销映射，保留旧版本和修订原因。
6. **迁移**：只把通过验证的映射用于新领域，并在整域留出/组合 OOD 上单独报告收益。

## 研究边界

- 本模块没有预填任何八卦物象、五行配属、卦德或爻辞解释。
- 本模块没有宣称经典语义已经被机器验证。
- 五行生克、阴阳消长、四象层次、卦序、卦气、爻位与时势应分别建立来源版本和独立实验，不得混成一个无出处的“易学标签表”。
- 合法的数据档案不等于真实的类象关系；所有映射仍需证据、反例和 OOD 评测。

## 验收

运行 `python -m unittest discover -s tests -p test_yixiang_profile.py`。新增测试覆盖八卦编码唯一性、名称/编码一致性、类型严格性、来源引用、ID 唯一性、冲突报告及范围隔离。
