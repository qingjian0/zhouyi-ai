# E02：动态超图发现与结构演化实验设计

## 1. 研究问题

E02 不以“使用超图”作为创新主张，而是检验：**在固定节点表示、监督信息和计算预算下，按任务反馈动态选择、更新高阶超边，是否比普通图、静态超图或随机超边更有效？**

核心变量：
- 超边阶数：2、3、4、5；
- 关系角色：无角色的无序集合 vs 有角色的有序槽位；
- 结构策略：固定候选、静态学习、动态 CREATE/PRUNE、完整 CREATE/MERGE/SPLIT/PRUNE；
- 候选预算：每轮最多 K 条边、每节点最大度数 D；
- 证据约束：无证据分数 vs 带来源/置信度的证据门控。

## 2. 数据任务设计

### E02-A：高阶联合约束识别

每个样本包含 n 个节点，每个节点有类型、属性向量和来源信息。目标关系由 3–5 个节点联合满足的约束定义。训练/测试按节点成员组合拆分，保证测试出现训练时未见的成员组合。

需要设置两类任务：
1. **可分解关系**：目标可由成对关系充分恢复，作为普通图模型应能解决的控制组。
2. **高阶协同关系**：目标依赖多个成员共同出现的联合条件，单独观察任意一对不足以确定标签。

第二类任务应加入 hard negatives：每个负样本都满足若干局部成对约束，但整体高阶条件不成立。否则模型可能通过简单 pairwise shortcut 取得高分。

### E02-B：动态环境变化

训练阶段的关系规则或节点分布按阶段变化。模型需要在不破坏旧结构的情况下创建、拆分或淘汰超边。分别测量新环境适应和旧环境遗忘。

## 3. 候选超边生成

对 n 个节点直接枚举所有子集会产生组合爆炸：
\[
\sum_{r=2}^{R}\binom nr
\]
因此分两阶段：

1. **候选召回**：类型兼容过滤、局部相关性检索、任务上下文约束、角色槽位约束，生成有限候选池。
2. **候选重排**：对每条候选超边计算高阶联合表示与关系分数，按 top-K 和预算约束保留。

候选生成器必须记录召回率。若正确超边没有进入候选池，后续打分器再强也无法恢复。

## 4. 高阶超边表示

无角色集合可用置换不变聚合：
\[
h_e=\mathrm{Pool}(\{Wz_i:i\in S_e\})
\]
有角色关系则必须显式编码角色：
\[
h_e=\mathrm{MLP}([W_1z_{i_1};W_2z_{i_2};\cdots;W_rz_{i_r}])
\]
关系得分：
\[
s(e)=f_\theta(h_e, c_t, q_e)
\]
其中 (c_t) 是任务上下文，(q_e) 是证据特征。应比较 sum/mean/max/attention pooling 和显式高阶交互项。

## 5. 结构生命周期

定义边效用：
\[
U(e)=\Delta L_{val}(e)-\lambda_c Cost(e)-\lambda_r Redundancy(e)
\]
其中 \(\Delta L_{val}\) 是在保留验证集上的任务损失改善。

- CREATE：新候选边带来稳定验证收益；
- MERGE：两条边高度重叠且合并后仍保留关系角色和证据；
- SPLIT：一条边内部出现稳定子群、角色冲突或残差双峰；
- PRUNE：边长期无增益、低证据支持或成本过高。

结构操作必须记录前后版本和触发证据。训练集损失下降不能单独作为永久保留边的理由。

## 6. 对照组

| 对照 | 结构 | 目的 |
|---|---|---|
| Pairwise Graph | 仅二元边 | 判断高阶建模是否必要 |
| Static Hypergraph | 固定超边，不更新 | 判断动态演化是否有贡献 |
| Random Hypergraph | 随机候选边 | 检查结构是否只是参数容量效应 |
| Dynamic CREATE/PRUNE | 仅增删 | 检查生命周期操作的必要性 |
| Full Dynamic Hypergraph | CREATE/MERGE/SPLIT/PRUNE | 完整机制 |
| Oracle Hypergraph | 使用真实关系结构 | 给出任务上界 |

参数量和计算预算应尽量匹配。若不能严格匹配，必须报告差异，不可把更大模型的收益归因于超图机制。

## 7. 评价指标

- 高阶关系 precision/recall/F1；
- 未见成员组合 exact match；
- 候选召回率；
- 超边数量、平均阶数、节点度数；
- 边冗余率、结构稳定性；
- 每轮更新边数、更新耗时；
- 训练/验证损失差距（过拟合）；
- 新分布收益与旧分布遗忘；
- 峰值内存、FLOPs 或可复现的计算代理指标。

## 8. 证伪条件

- 高阶协同任务上，普通图在匹配预算下表现相当或更好；
- 动态结构没有优于静态超图；
- 候选召回率过低，且增加预算后成本不可接受；
- 动态更新造成严重结构震荡或旧任务灾难性遗忘；
- 所谓增益仅来自参数量、训练步数或计算量增加。

出现这些结果时，应移除无效结构操作或缩小研究范围。

## E02-C：可审计结构生命周期原型

新增 `prototype/e02_edge_lifecycle.py`，以确定性状态机实现 CREATE、OBSERVE、MERGE、SPLIT、PRUNE 和最近一次操作回滚。每次结构变更保留事件日志与变更前快照。

关键约束：
- CREATE 要求成员唯一、角色一一对应、独立支持样本数达到阈值，且保留验证集收益超过门槛。
- MERGE 要求关系类型/重叠成员角色兼容、成员 Jaccard 达阈值，并且合并后的独立验证收益不能明显退化。
- SPLIT 要求子边完整且不重叠地划分父边成员、各自有足够支持，且子结构总验证收益超过父边。
- PRUNE 仅在连续多个评估窗口低于收益门槛后允许。
- 任何操作均可通过 rollback_last 恢复上一版结构；事件日志同步回退，便于重放。

该模块是结构治理与实验脚手架，不是学习算法。验证收益由外部评估器提供；本身不声称能自动发现正确关系。
