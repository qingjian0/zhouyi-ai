# E02-I2-C-F: Scenario Diversity and Metadata Invariance Preregistration

**Status:** preregistration only; no scenario-diversity result is claimed.  
**Dependency:** E02-I2-C-E metadata audit (PR #26).  
**Purpose:** determine whether event adjudication and metadata-leakage conclusions survive changes in the scenario-generation mechanism, rather than merely new random seeds.

## 1. Research question

Can the E02-I2-C event adjudicator distinguish lifecycle events when each event is generated by multiple independent scenario mechanisms and when non-semantic observation metadata is not uniquely associated with event labels?

A new seed on the same eight hand-authored templates is not scenario diversity. The test must vary the mechanism that produces the observable episode.

## 2. Threat model

The evaluator owns the event truth. The adjudicator and metadata attackers receive only an observation view. No event label, episode ID, seed, generator-family name, split name, or hidden scenario ID may enter predictive features.

Threats to detect:

1. **Template fingerprinting:** fixed event-to-window/evidence-count mappings.
2. **Provenance cardinality leakage:** record counts or duplicate patterns predict the event.
3. **Operational leakage:** sampling opportunity, coverage, missingness, environment, source-version count, or window spacing predict the event.
4. **Context-shape leakage:** identity status or candidate syntax predicts the event beyond what the evidence semantics justify.
5. **Generator-family leakage:** a classifier recognizes the generator family or serialization convention rather than the underlying event.

## 3. Scenario families and split design

At least four independently implemented generator families are required:

- **Family A — baseline temporal episodes:** current event semantics, but variable evidence and observation schedules.
- **Family B — reordered and resampled episodes:** independent observation order, variable sample grouping, and alternate valid provenance serialization.
- **Family C — environmental episodes:** multiple environments, observation noise, intermittent sampling, and source-version churn.
- **Family D — compositional episodes:** lifecycle events embedded in multi-relation contexts, with distractor relations and overlapping observations.

The development split must be family-disjoint:

| Split | Families | Use |
|---|---|---|
| Train | A + B | Fit metadata attackers and any tunable policy parameters |
| Gate | C | One-shot development evaluation after the protocol is frozen |
| Locked Test (future stage) | D plus a newly generated family | Final evaluation; unavailable to tuning |

No family may be represented in both Train and Gate by changing only the seed. Each family must have its own generator implementation or independently specified generative mechanism and its own version identifier held evaluator-side.

Minimum scale:
- At least 30 independent seed blocks per event per split.
- At least 8 lifecycle event classes.
- At least 3 environment conditions in the environment family.
- At least 2 independently authored scenario templates per event in each family where semantically valid.
- Every episode must retain evaluator-side provenance sufficient to reproduce it.

## 4. Nuisance factors and semantic constraints

The following nuisance factors should vary independently of event labels wherever the event semantics permit:

- evidence record count and identifier count;
- observation opportunity count;
- relative window gaps and observation order;
- sample grouping and sample reuse;
- coverage and missingness;
- environment labels;
- source-version presence/cardinality;
- raw-reference scheme and opaque identifier format.

Do not force impossible counterfactuals merely to balance a table. For example, a lifecycle transition may require multiple independent observations. Instead, define a semantic feasibility envelope for each event, then ensure that feasible nuisance profiles overlap across multiple event classes.

Separate feature groups:
- **M0:** opaque identifier surface and cardinality only.
- **M1:** operational/provenance metadata.
- **M2:** context shape (identity presence/status and coarse candidate syntax).
- **Evidence semantics:** polarity, support/contradiction, candidate binding, and temporal evidence. These are not metadata attackers' inputs; they are adjudicator inputs.

Identity status and candidate shape are not automatically nuisance variables. They may be legitimate context. Their predictive power must be reported separately and compared with evidence-aware adjudication.

## 5. Required anti-shortcut checks

Before training any attacker:

1. Assert Train/Gate sample and evidence namespaces are disjoint.
2. Assert evaluator-only truth, seeds, split markers, family IDs, and episode IDs are absent from observation features.
3. Assert absolute window indices are excluded; only relative timing may be used.
4. Report per-event distributions for evidence count, opportunity count, window count, coverage, missingness, source-version count, and identity status.
5. Report cross-event overlap of each metadata profile and identify features that are deterministic or near-deterministic proxies for an event.
6. Verify bijective opaque-ID renaming invariance.
7. Verify that permuting observation order where semantics are order-invariant does not change the adjudication result.
8. Verify that changing a nuisance factor within the declared semantic feasibility envelope does not change event truth or the adjudicator's expected decision.

Any feature that is a deterministic event proxy must be disclosed. Do not silently remove it after observing Gate performance; preregister a revised protocol and rerun with a new Gate family.

## 6. Attackers and metrics

Retain the E02-I2-C-E baselines:
- majority class;
- categorical Naive Bayes;
- deterministic depth-3 categorical decision tree.

Evaluate M0, M1, and M2 independently, with:
- accuracy and macro-F1;
- per-class precision, recall, F1, and confusion matrix;
- majority-baseline lift;
- 95% seed-block bootstrap intervals;
- per-family and per-environment breakdowns.

Keep the evidence-aware adjudicator as a reference policy, not as a metadata attacker.

Preregistered M0 alarm:
- Macro-F1 lift over majority is at least 0.05; and
- the 95% seed-block bootstrap interval for lift excludes zero.

M1/M2 are diagnostic: high scores identify operational/context correlations but are not by themselves proof of invalid reasoning, because some context can be semantically relevant. The report must distinguish legitimate evidence context from generator fingerprints.

## 7. Negative controls

- Train-label permutation.
- Random opaque-ID replacement and bijective ID renaming.
- Within-class nuisance-factor permutation, preserving event truth.
- Family-label permutation (family labels must never be exposed to attackers).
- A metadata-only attacker trained on A+B and evaluated on C without Gate tuning.
- Evidence-aware policy under nuisance transformations that preserve semantics.

Negative controls must be reported even when they fail. No post-hoc threshold or feature selection on Gate.

## 8. Stop conditions

Stop and redesign before Locked Test if:
- M0 triggers the preregistered leakage alarm;
- any split/family/seed/episode identifier reaches the attacker;
- Train/Gate namespaces overlap;
- a supposedly nuisance-only transformation changes event truth or adjudicator semantics;
- Train and Gate share a generator template family;
- any generator family is only a seed variation of another family.

## 9. Interpretation boundaries

Passing this experiment would support robustness to the tested scenario-generation mechanisms. It would not prove open-world relation discovery, causal discovery, or general intelligence.

A failure is useful: it identifies which event distinctions depend on generator-specific assumptions and which require stronger evidence representations or abstention.

## 10. Execution order

1. Finish E02-I2-C-E feature-family ablations and review the latest CI artifact.
2. Freeze event semantics and the semantic feasibility envelope.
3. Implement Families A–D in a new module without changing PR #16's hidden-event benchmark.
4. Validate invariance and anti-shortcut checks before running attackers.
5. Run Train A+B and Gate C once; publish complete reports.
6. Only after review, preregister a separate locked-Test stage.
