# ZNCA N3：事件驱动的局部关系认知架构

日期：2026-11-11  
状态：架构研究提案；未实现、未训练、未通过性能验证  
依赖：ZNCA N1 relational state substrate、N2 relational dynamics、XSL-1～XSL-5

## 1. 设计目标

N3 不是把 Transformer 的 Q/K/V、token 序列或 KV Cache 改名。它尝试定义一种不同的认知计算循环：

`Observation Event → Local Retrieval → Candidate Hypotheses → Local Dynamics → Evidence Arbitration → State Commit/Revise → Language Realization`

核心计算对象是有类型、有角色、有时间和证据来源的状态与关系；文本只是观察输入和最终表达的一种载体。

## 2. 与 N1 / N2 的关系

- N1：保存事件、实体、角色关系、证据来源和可撤销断言；提供有界关系查询。
- N2：在已给定候选关系项上计算状态转移，并拟合影响权重。
- N3：决定何时检索哪些局部状态、提出哪些候选关系/规则、在哪些状态子图上运行 N2、如何保留竞争假设，以及何时提交或回滚状态更新。

N3 不重写 N1 的事件账本，也不复制 E12/E13 的候选生命周期和证据裁决职责。

## 3. 七个运行阶段

### 3.1 Observation Gateway

将文本、图像、工具结果或传感器数据转换为带来源的观察事件。每条 observation 必须保留原始来源引用、时间、抽取方法和不确定字段。模型抽取的关系不得直接标记为 OBSERVED，必须记录为 INFERRED 或待验证候选。

### 3.2 Local State Retrieval

根据事件涉及的实体、关系类型、角色和时间范围，从 N1 索引检索局部工作集。查询必须携带扫描预算、结果上限和完成状态；预算耗尽必须显式返回，不得伪装为 NOT_FOUND。

工作集是临时计算窗口，不是完整记忆。未进入工作集的历史事实仍可由外部事件账本与索引检索。

### 3.3 Candidate Hypothesis Generation

基于局部图提出候选关系、规则、类象映射或角色变换。候选必须有：
- 候选 ID 和版本；
- 来源观察 / 证据引用；
- 适用条件；
- 预测后果；
- 反例与反事实条件；
- 计算成本估计；
- 生命周期状态。

候选生成不等于事实写入。一个观察可以产生多个互相竞争的假设。

### 3.4 Local Relational Dynamics

只在受影响的状态子图上调用 N2 类型的关系动力学算子。事件更新依赖图索引维护 dirty set：
- 新观察触及的实体/关系；
- 其直接依赖项；
- 在预算内允许的有限多跳依赖。

不得默认全图重算。若影响范围超预算，返回 PARTIAL / BUDGET_EXHAUSTED，并将未计算范围列明。

### 3.5 Hypothesis Arena

并行保存多个候选状态增量（delta），每个候选独立计算预测后果。候选之间不能共享可变状态对象；一个候选失败不得污染其他候选或已提交状态。

候选数量、展开深度、每候选算子数和总计算量均有硬预算。候选剪枝必须保留被剪枝原因和可恢复来源。

### 3.6 Evidence Arbitration and Commit

比较预测与新观察、已有证据、适用条件和反例。只有通过项目既有 E09/E12/E13 的证据与生命周期门槛，候选才能被提交为新的状态版本。

提交前后保留：
- parent state version；
- candidate version；
- evidence refs；
- operator/version；
- predicted vs observed outcomes；
- commit / reject / defer reason。

撤销是追加新事件，不是删除历史证据。发生冲突时保留 CONTESTED 状态，不强行覆盖。

### 3.7 Language Realization

言语生成读取已经裁决的状态视图，负责组织答案、说明证据和表达不确定性。语言模型可以作为接口/渲染器，但不应通过润色文字反向改变事实状态或证据极性。

## 4. 核心计算模型

N3 的一次事件处理不必更新全部状态。令：
- (G=(V,E)) 为持久关系状态；
- (Delta_t) 为新观察事件；
- (A_tsubseteq Vcup E) 为受影响局部工作集；
- (H_t) 为竞争假设集合；
- (B_r,B_h,B_o) 分别为检索、假设和算子预算。

处理流程：
1. 由索引计算候选工作集 (A_t)，受 (B_r) 限制；
2. 生成至多 (B_h) 个候选假设；
3. 每个候选只在受影响依赖子图上运行至多 (B_o) 个算子；
4. 得到一组候选 delta，而不是立即覆盖 (G)；
5. 由证据门控决定 commit、reject、defer 或 partial。

在索引有效且局部依赖稀疏时，单次工作量可与受影响邻域相关；但最坏情况仍可能扩展到全图，不能宣称 O(1) 或固定常数时间。

## 5. 与 Transformer 的根本区别及现实边界

| 维度 | Transformer 主路径 | N3 候选路径 |
|---|---|---|
| 主要计算对象 | token 表示与注意力交互 | 事件、状态、关系、候选 delta |
| 更新触发 | token 序列前向计算 | 新事件与受影响依赖 |
| 长期记忆 | 外部检索 + 模型上下文/KV | 事件账本 + 索引 + 有界工作集 |
| 推演方式 | 隐式表示中的层级计算 | 显式关系算子与竞争假设 |
| 证据治理 | 需额外系统约束 | 作为状态提交协议的一部分 |
| 表达 | 自回归 token 生成 | 独立 realization 层，可调用语言模型 |

N3 不是天然优于 Transformer。Transformer 在感知、语言表达、模糊模式识别和大规模预训练方面有成熟优势。N3 的待验证假设是：显式关系状态与事件驱动局部更新，可能在结构化长期状态、可追溯推演和受限设备工作集方面提供不同的性能/可控性权衡。

## 6. 手机内存与上下文策略

N3 必须区分：
- **持久知识量**：外部事件账本与索引能存多少；
- **有效上下文**：一次任务检索并装配多少相关证据；
- **活动工作集**：本次推演中实际驻留内存的实体、关系和候选；
- **模型激活内存**：编码器、动力学算子或语言模型本身的运行内存。

不把完整历史转为 token，也不把全部关系图加载进 RAM。采用分层存储、索引检索、局部加载、版本化快照和按需卸载。手机上仍需实测索引常驻成本、随机 IO、冷启动、缓存命中、峰值 RSS、电量和热降频。

## 7. 必须实现的事务语义

1. 候选隔离：候选 delta 不得直接修改已提交状态。
2. 原子提交：一次 commit 要么完整落账，要么不生效。
3. 幂等事件：重复 event_id 不重复应用。
4. 版本冲突：parent version 过期时拒绝盲目提交，必须重算或显式 rebase。
5. 预算耗尽：保留部分结果和未完成标志。
6. 崩溃恢复：事件日志与状态快照必须能重建一致状态。
7. 可撤销：撤销以新事件表达，历史不可静默抹除。
8. 来源闭环：每个已提交关系和状态更新都可追溯到观察或明确标注的推断。

## 8. N3 最小可行原型路线

N3-A：Dirty-set scheduler
- 从 N1 新事件找出受影响的 relation IDs；
- 计算有限邻域；
- 统计扫描数和预算耗尽情况。

N3-B：Hypothesis arena
- 为多个候选创建隔离状态 delta；
- 支持 commit / reject / defer；
- 验证候选失败不污染基线状态。

N3-C：Transactional commit
- 基于 parent version 做 compare-and-swap；
- 原子写入状态变更和事件；
- 崩溃注入测试和重放一致性。

N3-D：Evidence-gated dynamics
- N2 输出预测，不直接写事实；
- 对照新观察和反例；
- 通过 E09/E12/E13 既有门槛后提交。

N3-E：Mobile profiling
- 固定设备和数据集；
- 报告 RSS、工作集大小、冷/热查询延迟、每事件算子数、磁盘 IO、能耗和热状态；
- 与全图重算、RAG+小模型、图数据库检索等基线比较。

## 9. 证伪条件

若局部调度在真实稀疏工作负载下没有降低峰值内存或总计算成本；若候选隔离/提交机制带来不可接受的延迟；若 N2 的状态转移无法在真实观察中预测后果；或若更简单的图检索 + 小模型达到同等效果，则应简化 N3，而不是为了“新架构”保留复杂度。

## 10. 当前声明

本文件是架构提案，不是可运行 N3 实现。N1/N2 的存在不等于 N3 已经具备自主学习、原始多模态感知、通用推理或 Transformer 替代能力。下一步先实现 N3-A 与 N3-B 的小型事务原型，再用基准决定是否继续。
